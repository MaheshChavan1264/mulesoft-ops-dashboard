# Backend Analysis Report — mulesoft-dashboard

**Scope:** `backend/src/**` (18 files — server bootstrap, 9 route modules, 7 utils, 1 middleware)
**Date:** 2026-04-10 · **Branch:** `refactor/frontend-restructure`

This backend is an Express proxy/aggregator in front of the Anypoint Platform API, API Manager, CloudHub 1/2, Exchange, and self-hosted CPS (Configuration Property Server) instances. It is generally well-commented and already has some solid patterns (SWR caching, thundering-herd guards, keep-alive agents for Anypoint calls). The issues below are organized by severity/category so they can be triaged independently.

---

## 1. Bugs & Correctness Issues

| # | Location | Issue |
|---|----------|-------|
| 1.1 | `routes/health.js` `buildBaseUrl` / ping loop (142-386) | **Unbounded worst-case latency.** Up to 3 base URLs × 6 paths = 18 sequential attempts, each with a **30s timeout**, run one after another. A fully unreachable app can take up to **9 minutes** before the endpoint returns `FAILED`. There is no overall deadline (`AbortController`/`Promise.race`) capping total wall-clock time. |
| 1.2 | `routes/cps.js` — `/fetch`, `/search-user` vs `/write`, `/auth`, `/project`, `/binary`, `/credentials/test` | **Inconsistent TLS handling.** `/fetch` and `/search-user` pass the module-level `httpsAgent` (`rejectUnauthorized: false`) so self-signed/internal-CA CPS servers work. The write-path routes (`/write`, `/auth`, `/project`, `/binary`, `/credentials/test`) build their own `axios.get/post/put/delete` calls **without** that agent, so the same CPS server that works for reads will fail TLS verification on writes. This is a functional bug waiting to surface on any CPS host with an internal CA. |
| 1.3 | `routes/auth.js` `storeSession` (9-76) | `rootOrg` can be `undefined` if `memberOrgs` is empty **and** `user.organization` is also missing — `rootOrg.id` on line 23 would throw an unhandled exception inside the route's try block (caught generically, but the user gets an opaque 500 instead of a clear "could not determine organization" message). |
| 1.4 | `routes/cps.js` helpers export (1317-1320) | `detectEnvType`, `detectChType`, `getCredentials`, `normaliseUrl` are bolted onto the `router` object (`router.detectEnvType = detectEnvType`) purely so they *could* be reached from outside — but nothing else requires `routes/cps`. This is dead/confusing code and not a real module boundary (see §4.3). |
| 1.5 | `server.js` (89-100) | `secret: SESSION_SECRET || DEFAULT_SECRET` is evaluated again at session-middleware setup even though the fail-fast check above already exits the process in production when the secret is missing — harmless today, but it re-introduces the insecure default as a silent fallback path if the early-exit logic is ever refactored away. |
| 1.6 | `routes/health.js` `/ping` and `/oauth2-token`, `routes/cps.js` `/fetch`/`/write`/`/binary` | **SSRF surface.** `ch2IngressUrl`, `tokenUrl`, and CPS `baseUrl` are attacker/user-supplied strings used directly as outbound request targets with no host allow-list. Any authenticated session can make this server send credentials (`clientId`/`clientSecret`/`bearerToken`) to an arbitrary host, or use `/api/health/ping` as a generic internal-network HTTP probe. Likely acceptable for a trusted internal tool, but should be a conscious decision, not an oversight — see §2. |
| 1.7 | `routes/applications.js` CH1/CH2 action/scheduler toggles | No idempotency/locking: two concurrent `start`/`stop` calls for the same app will both execute strategy chains independently; no `409`/in-flight guard, which can cause the stop→wait→start restart sequence to interleave unpredictably with a parallel manual action. |

## 2. Security

| # | Location | Issue | Suggested fix |
|---|----------|-------|----------------|
| 2.1 | `utils/anypointClient.js` *not* affected, but `routes/health.js:8`, `routes/cps.js:8` | `new https.Agent({ rejectUnauthorized: false })` disables TLS certificate verification **globally for every outbound call made through it** (ping targets, CPS fetches). This defeats MITM protection for every self-hosted/internal endpoint this backend talks to, including ones that *do* carry client secrets. | Replace with a custom CA bundle (`ca: fs.readFileSync('internal-ca.pem')`) loaded from env/config so verification stays on but trusts the internal CA. |
| 2.2 | `server.js:58-61` | CORS origin list is hardcoded to `localhost:5173`/`localhost:3000` — breaks for any real deployment and silently requires a code change (and redeploy) to add a prod origin. | Load from `CORS_ORIGINS` env var (comma-separated), parsed once at boot. |
| 2.3 | §1.6 (SSRF) | No allow-list / private-IP block on user-suppliable outbound URLs (`ch2IngressUrl`, `tokenUrl`, CPS `baseUrl`). | At minimum, document this as an accepted-risk "trusted internal tool" posture, or add a hostname allow-list (`*.internalapi.sfdcbt.net`, configured CPS hosts only). |
| 2.4 | `routes/cps.js` session storage | CPS `clientId`/`clientSecret` pairs are stored **unencrypted** in `req.session.cpsCreds`, which is itself persisted unencrypted to `sessions.db` on disk (via `sqliteSessionStore.js`). Anyone with filesystem access to the server reads every uploaded CPS credential in plaintext. | Encrypt the `cpsCreds` sub-object with a server-side key (e.g. AES-GCM via Node's `crypto`) before storing in the session, decrypt on read. |
| 2.5 | No security headers | No `helmet()` (or manual CSP/`X-Content-Type-Options`/`X-Frame-Options`) anywhere in `server.js`. | Add `helmet()` with a CSP tuned for the SPA. |
| 2.6 | `routes/health.js` ping_history / `routes/cps.js` logs | `credentialsLabel` is persisted to the `ping_history.credentials` column and client IDs are logged (truncated) to stdout. Low risk since truncated, but confirm no full secrets ever reach `console.log`/DB — a quick grep today shows only prefixes logged, which is good; keep this discipline enforced by a lint rule or helper (`maskSecret()`) rather than manual slicing at each call site. | Extract a `maskSecret(str, n=8)` helper used everywhere instead of ad hoc `.slice(0,8)`. |
| 2.7 | Rate limiting | Only `/api/auth/*` is rate-limited, and **only in production** (`skip: NODE_ENV !== 'production'`). `/api/health/ping`, `/api/cps/search-user` (which fans out up to 30-concurrent requests per call) and all write endpoints have no limiter — a buggy frontend loop or malicious client can hammer both this server and every downstream Anypoint/CPS/internal host. | Add a general-purpose limiter (e.g. 100 req/min/session) on `/api/*`, with a higher ceiling for read endpoints and a lower one for `search-user`/`ping`. |
| 2.8 | No CSRF token | Relies solely on `sameSite: 'lax'` cookies for CSRF protection on state-changing routes (POST/PUT/DELETE across apps/cps/health). Reasonable baseline, but no defense-in-depth. | Consider a double-submit CSRF token for the highest-impact routes (CPS write/delete, app start/stop). |
| 2.9 | No RBAC beyond "has a valid Anypoint token" | Every destructive capability (CPS write/delete, binary upload, start/stop/restart apps, scheduler toggles, contract delete) is available to any authenticated session with no extra confirmation/role gate at the dashboard layer — fully delegated to Anypoint's own permission model. | Acceptable if intentional; otherwise add an app-level "write-access" role check. |
| 2.10 | `routes/cps.js` write/delete | CPS **write/delete operations are only logged to console**, never to the `app.db` SQLite audit trail that already exists for pings. Given these mutate production configuration, there's no durable audit log of who changed what. | Add a `cps_audit_log` table (`db.js`) and insert a row on every write/delete/auth-change, mirroring the existing `ping_history` pattern. |

## 3. Performance

| # | Location | Issue | Suggested fix |
|---|----------|-------|----------------|
| 3.1 | `routes/health.js` ping loop | See §1.1 — biggest single performance problem in the codebase. | Run the first N candidate URLs with a short per-call timeout (e.g. 5-8s) in small parallel batches via `Promise.any`/`allSettled`, and cap total ping time with one outer deadline (e.g. 25s) instead of `paths × bases × 30s`. |
| 3.2 | `routes/exchange.js` `/ping-spec` asset search (166-282) | Nested **sequential** loops: `searchStrategies × searchTerms` awaited one at a time, then `assetIdVariants × orgIds` awaited one at a time. Each iteration is a full HTTP round trip; worst case is dozens of sequential calls before falling back. | Parallelize independent probes with `Promise.allSettled` + a concurrency cap (e.g. 5), short-circuiting as soon as a strong match (`score ≥ threshold`) is found. |
| 3.3 | `routes/cps.js` `/search-user` `processApp` fan-out (788-811) | Concurrency is "batches of 30, await full batch, then next batch" — a single slow app in a batch of 30 blocks the next batch from starting even if 29 of 30 already resolved. | Switch to a real concurrency pool (`p-limit`, or a tiny semaphore) that keeps a constant number of in-flight requests instead of lock-stepping in fixed batches. |
| 3.4 | `routes/cps.js` write-path routes (`/write`, `/auth`, `/project`, `/binary`, `/credentials/test`) | Use plain `axios.get/post/...` with the **default (non-keep-alive) agent** — every call pays a fresh TCP+TLS handshake, unlike `/fetch`/`/search-user` which reuse the module-level agent. | Reuse a single keep-alive `httpsAgent`/`httpAgent` pair across all CPS calls (same pattern as `utils/anypointClient.js`). |
| 3.5 | `utils/db.js`, `utils/sqliteSessionStore.js` | `node:sqlite`'s `DatabaseSync` runs **synchronously on the event loop** for every read/write (ping history inserts/selects, session get/set/touch on *every* request). At low traffic this is invisible; under concurrent load it adds latency spikes shared across all in-flight requests. | Acceptable for current scale; if traffic grows, consider `better-sqlite3` (still sync but faster) or moving session/ping writes off the hot path (e.g. batched/async). |
| 3.6 | Query params like `limit`/`offset` (`apis.js`, `applications.js`, `organizations.js`) | Taken straight from `req.query` with no clamping — a client could request `limit=999999999`, forwarding an expensive query to Anypoint. | Clamp with `Math.min(Number(limit) || 50, 200)` style helper. |
| 3.7 | `summaryCache` / `detailCache` (NodeCache, in-process) | Fine for a single instance; if this is ever horizontally scaled behind a load balancer, each instance has its own cold cache and the thundering-herd guard only protects within one process. | Note as a scaling limitation; move to Redis-backed cache only if/when multi-instance deployment happens. |

## 5. Best Practices / Process Gaps

1. **No automated tests anywhere** (no `*.test.js`, no test runner in `package.json`). The pure-function utils (`appHelpers`, `orgHelpers`, `responseHelpers`, `exchangeHelpers`) are trivially unit-testable today and would be a cheap first step; the CPS credential-retry logic in `cps.js` is exactly the kind of code that silently regresses without tests.
2. **No ESLint/Prettier config** despite `server.js:141` containing an `eslint-disable-next-line` comment that implies linting was expected at some point. Add a shared config (align with whatever the frontend uses) and a `lint` script.
3. **No centralized logger.** Every file uses `console.log/warn/error` with hand-rolled tags (`[Ping]`, `[CPS Write]`, `[auto-credentials]`, `[Summary]`). Several call sites in `applications.js`/`cps.js` have debug lines **commented out** rather than gated behind a log-level/env flag (e.g. `applications.js:637,671,677,691,695`). Adopt `pino`/`winston` with levels, and delete or re-enable-via-flag the dead commented logs.
4. **No request validation library.** Manual `if (!x) return res.status(400)` checks are inconsistent — some validate type (`typeof enabled !== 'boolean'`), most don't (e.g. `action` body field, CPS `type`/`method` are checked, but plenty of query params aren't). Standardize on `zod` or `express-validator` schemas per route.
5. **No config module.** `process.env.X` is read ad hoc throughout (`server.js`, `anypointClient.js`, `cps.js`), with `.env.example` only documenting a subset (missing `SESSION_DB_DIR`, `CORS_ORIGINS` if added, etc.). A single `config/index.js` that reads and validates all env vars once at boot would self-document requirements and simplify testing/mocking.
6. **No graceful shutdown.** `app.listen(...)` return value is discarded; no `SIGTERM`/`SIGINT` handler to close the HTTP server and the two `DatabaseSync` handles (`db.js`, `sqliteSessionStore.js`) cleanly before exit — fine for `nodemon` dev loops, risky for container orchestration (SIGTERM during a rolling deploy).
7. **Magic numbers scattered.** Timeouts (`5000`, `8000`, `10000`, `15000`, `20000`, `30000`, `60000`) and retry batch sizes (`5`, `30`) appear as bare literals throughout `cps.js`/`health.js`, inconsistent with the well-named constants pattern already used for cache TTLs in `applications.js`. Promote them to named constants in one place.
8. **No OpenAPI/Swagger spec.** This backend aggregates a large, non-trivial API surface (9 route files, Anypoint + CPS + internal ping targets); an OpenAPI doc would materially help onboarding and the frontend contract.
9. **No CI pipeline** evident (no `.github/workflows` checked, no lint/test script to run in one) — once tests/lint exist, wire them into CI.
10. **Dependency hygiene** — add `npm audit`/Dependabot given this proxies credentials for multiple external systems; a compromised transitive dependency here is high-impact.

## Suggested Priority Order

1. **Fix the ping timeout cascade** (§1.1 / §3.1) — directly affects every user's experience checking app health, worst case ~9 minutes.
2. **Fix inconsistent CPS TLS/keep-alive agent usage** (§1.2 / §3.4) — latent correctness bug that will manifest unpredictably per CPS host.
3. **Encrypt CPS credentials at rest in session storage** (§2.4) and **add a CPS write/delete audit table** (§2.10) — both touch real secrets/production config.
4. **Introduce `asyncHandler` + extract CPS/health helper functions into `utils/`** (§4.1, §4.3, §4.6, §4.7) — the single highest-leverage refactor for maintainability and testability, and a prerequisite for writing tests.
5. **Add unit tests for existing pure utils** as a quick win while the extraction in (4) is happening.
6. Everything else (CORS env-driven config, helmet, rate limiting breadth, logger, config module, OpenAPI) as follow-up hardening.
